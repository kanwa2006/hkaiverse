## 3. Reasons for Redesign

### Reason 1 — Students Learn Components but Not Integration
Current courses teach programming, databases, web, and networks separately. Students may pass all of them without ever building a working application that connects a frontend, a REST API, a database, and error handling in one system. This gap shows up immediately in a first job.

### Reason 2 — REST API Skills Are Not Systematically Practised
All three job descriptions reviewed (ACHNET SDE, JPMorgan Data Analyst, Joveo Full-Stack Intern) list REST API knowledge or web backend skills as a core requirement. The current CS205 Web-Enabled Technologies course covers web concepts, but a hands-on lab where students design and test a REST API connected to a database does not appear to be present (student observation). This is a practical gap.

### Reason 3 — Git and Version Control Are Not Assessed
Git-based collaboration is listed as a requirement in every job posting reviewed. Students in CS304 Software Engineering may encounter Git in theory, but there is no course where students are assessed on using Git for collaborative development. This means students may apply for roles without the basic workflow knowledge that every engineering team uses daily.

### Reason 4 — No Systematic Unit Testing Practice
Hands-on software testing is expected in all three reviewed job descriptions — Joveo expects working shipped code, JPMorgan expects data quality checks, and the ACHNET JD lists testing as part of the full development lifecycle. The current curriculum covers software testing concepts in CS304, but does not appear to include a lab where students write, run, and interpret test cases for their own code. Students should practise this in every programming course, not only learn about it once.

### Reason 5 — Assessment Weighted Towards Theoretical Examination
The student-reported assessment pattern (50% internal, 50% external, external entirely theoretical) means that a student can score well without ever demonstrating a working system. Practical engineering ability requires demonstrating, explaining, and debugging — not only answering written questions.

### Reason 6 — Confidence at the Start of a First Job
Industry and faculty feedback (informal, see `FEEDBACK_AND_LIMITATIONS.md`) both pointed to the same concern: students who have built something complete feel less lost in the first few months of a job. Students who have only seen components in isolation may understand what to do individually but not how to start a task that crosses multiple systems. The proposed lab directly addresses this.

### Reason 7 — The Curriculum Has the CS Foundations Right but the Application Layer Thin
The programme retains strong fundamentals: discrete mathematics, theory of computation, algorithms, OS, networks, DBMS, OOP, AI/ML. These are the right subjects. The proposal does not remove any of them. The gap is not in what is taught — it is in the opportunity to use these skills together in a guided, assessed project before graduating.

### Reason 8 — Cloud and Deployment Are Growing Requirements
CS307 Cloud Computing is present. But learning about cloud architectures without ever deploying a small application to a cloud service leaves students knowing the concepts without the practical confidence. The proposed UPDATE to CS307 adds a hands-on deployment exercise.

### Reason 9 — Practical Credits Funding: Three Courses Are Reasonable Candidates for Reduction
- **PH101 Physics (5 → 4):** Five credits is a heavy allocation for a course that provides engineering context rather than directly applicable CS skills. A one-credit reduction to free a credit for a practical computing lab is justifiable.
- **MG201 Engineering Economics and Management (3 → 2):** The core concepts of this course can be preserved in two credits. The reduction creates space for the new lab.
- **HS201 Dynamics of Social Change (3 → 2):** Social awareness is valuable and should be retained. A one-credit reduction still allows the essential learning outcomes to be covered.

These are proposals, not decisions. Each requires formal academic approval.

### Reason 10 — Progressive Project Complexity Is a Proven Learning Model
Starting with small exercises (Semester I) and progressively increasing complexity — from individual components (Semesters II–IV) to integrated projects (Semesters V–VI) and then the six-month internship (Semester VIII) — is an established approach to building engineering competence. The current curriculum has this progression in theory but lacks a guided integration project between the component-level courses and the open internship.

### Reason 11 — AI-Assisted Development Requires Verification Skills
Students are increasingly likely to use AI tools at work. The AI exercises in this report demonstrate that AI tools produce correct foundational answers but miss important nuances — performance issues, edge cases, design trade-offs. Students need practice in using AI output as a starting point and then verifying, testing, and improving it. This is a new applied skill that deserves explicit curriculum attention.

### Reason 12 — The Existing Special Project (SP301) Is a Starting Point, Not a Replacement
SP301 Special Project in Semester VI provides a project experience. The proposed CS-NEW lab is designed as a more structured, assessed, engineering-process-focused experience — one that requires requirements writing, testing, error handling, and documentation in addition to building something. These are complementary, not redundant, if placed thoughtfully.

### UPDATE Courses (content or practical emphasis improved)

| Course | Update Proposal |
|---|---|
| **CS101** Computer Programming | Add Git basics (clone, commit, push); introduce unit testing with pytest; add debugging exercises; include a small exercise on AI-assisted coding with manual verification. |
| **CS102** Data Structures | Add implementation labs: students write, test, and analyse the time complexity of stack, queue, linked list, and binary tree implementations. Add at least one timing experiment comparing O(n) vs O(n²) on real inputs. |
| **CS205** Web-Enabled Technologies | Add REST API design lab: students design a 3-endpoint API (create, read, update), implement it in Python (Flask or FastAPI), connect it to a SQLite database, and test it with curl or Postman. |
| **CS206** Database Management Systems | Add SQL practice exercises: 10+ written queries progressing from simple SELECT to multi-table JOINs, aggregations, and transactions. Add a schema design exercise where students normalise a realistic table to 3NF. |
| **CS302** Operating Systems | Add shell scripting lab: students write a bash script that creates directories, processes files, and uses pipes. Add a process scheduling simulation where students compute AWT for FCFS, SJF, and Round Robin on the same process set. |
| **CS304** Software Engineering | Add Git workflow lab: students work in pairs, create branches, resolve a merge conflict, and submit a pull request. Add a requirements tracing exercise and a one-page design document for a small feature. |
| **DS304** Machine Learning | Add practical model building: students split a provided dataset (train/test), train a classifier, evaluate with confusion matrix and F1-score, and identify one overfitting indicator. |
| **CS307** Cloud Computing | Add a hands-on lab: students deploy a small Flask application to a free cloud platform (e.g., Render, Railway, or equivalent) and verify it is accessible. Add a brief Docker containerisation exercise. |
| **CS415** Ethical Hacking | Add a secure coding lab: students review three code snippets with known vulnerabilities (SQL injection, unvalidated input, hardcoded credentials) and fix them. Add a basic port-scan exercise in a controlled lab environment. |

## 5. Assessment Improvement Proposal

### Current Pattern (Student-Reported Understanding)

The student understands the current assessment as follows:
- Internal assessment: 50% of total mark
- External assessment: 50% of total mark
- Within internal: approximately 30% written test, 30% practical
- External: entirely theoretical written examination

This is the student's understanding of the assessment pattern. It has not been verified against an official IFHE regulation document.

### Proposed Assessment Direction

For courses with significant practical components (CS101, CS102, CS205, CS206, CS302, CS304, DS304, CS-NEW), the proposal is to evaluate a more practical-focused split:

**Proposed (for applicable courses):**
- Practical / laboratory assessment: 60%
- Written / theoretical assessment: 40%

### What Practical Assessment Could Include
- Demonstrating a working solution in a live session.
- Writing and running test cases for provided code.
- Debugging a given problem in real time.
- Explaining a design decision: why this data structure, why this query type.
- Integrating two components (e.g., connecting a backend API to a database query).
- Handling an error or edge case introduced by the assessor.

### Why This Matters
A student who can explain a linked list in a written answer but cannot implement one and check that it handles edge cases (empty list, single element, large input) has not fully achieved the learning outcome. Practical assessment makes the learning visible. It also better prepares students for the live coding and system-design interviews that are standard in entry-level software engineering hiring.

**Regulatory note:** Any change to the assessment split requires review and approval under applicable IFHE academic regulations. This is a proposal, not a policy recommendation.
